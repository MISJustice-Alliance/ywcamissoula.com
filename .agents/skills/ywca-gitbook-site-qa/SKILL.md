# YWCA GitBook site QA

## When to use
Use for pre-push checks, broken-link or navigation audits, post-publish smoke tests, SEO metadata, and Cloudflare structured-data troubleshooting in `~/projects/ywcamissoula.com/`.

## Procedure
1. Read `DEPLOYMENT.md`, `SEO_GEO_AEO_FINDINGS.md` (dated observations, recheck live), `tools/validate_site.py`, `tools/smoke_endpoints.txt`, `gitbook-export/SUMMARY.md` and `.gitbook.yaml`. Check `git status --short`; do not modify unrelated changes.
2. From repo root run `/usr/bin/python3 tools/validate_site.py gitbook-export` and `/usr/bin/python3 -m pytest tools/tests/test_validate_site.py -q`. This host's Hermes `python3` lacks PyYAML and pytest; use an interpreter with `tools/requirements.txt` installed if `/usr/bin/python3` changes. This validator covers SUMMARY targets, description frontmatter, includes, relative links, redirects, and duplicate title/description warnings; it does not prove every legal claim or every unpublished page correct.
3. For a published-site request, run `/usr/bin/python3 tools/validate_site.py gitbook-export --live tools/smoke_endpoints.txt`. After an authorized push, read back `git ls-remote origin refs/heads/main` and compare with local HEAD; then separately inspect the GitHub workflow for that SHA and check the target URL and GitBook `/sitemap-pages.xml`. A successful push does not prove GitBook has synced: if the workflow is still running or the URL returns 404, report remote code as pushed and live publication as unverified rather than promising delivery. Verify final status, canonical, rendered title/description, and whether old URLs redirect. For research-report mastheads, check that the GitBook-rendered frontmatter description appears once beneath the H1, not again as a body subtitle; compare source and fresh live `.md`/HTML (not only cached extraction) before changing anything. The source heading, metadata description, and rendered body are different surfaces: retain the top description and remove only a redundant body line. Inspect the article-specific masthead labels and links against the `ywca-gitbook-editor` skill's report-opening template without forcing copied wording. Treat network failures or unsynced live output as unverified, not passed. A page containing `challenge-platform` or `Just a moment` is not alone a Cloudflare challenge; check status, `cf-mitigated`, and actual response content.
4. Edge metadata and root-file changes belong in `cloudflare/structured-data-worker/`; read its README, route config, and Worker implementation. GitBook Git Sync does not publish repo-root files: map a verification URL to the source file's exact bytes in `staticTextFiles`, then test `GET`, `HEAD`, MIME type, and origin bypass. For a homepage verification meta tag, inject it once inside `<head>` on HTML `200` responses only, without adding it to other pages. For agent-discovery `Link` headers, first verify the target resource exists, choose a relation that truly describes it (`describedby` for the existing machine-readable site overview), append rather than replace origin Link values, and test GET and HEAD without advertising nonexistent API catalogs or service descriptions. For `/auth.md`, inspect the actual response body rather than trusting status `200`: GitBook can return a Markdown “Page Not Found” with HTTP 200. If no real agent-registration endpoint or OAuth issuer exists, serve an honest public-access document with an `auth.md` H1 and Markdown MIME; do not invent protected-resource metadata, OAuth issuers, registration methods, or token flows to satisfy a scanner. Run `npm test` and a Wrangler dry-run bundle from that directory; inspect test output for runtime exceptions even when the runner exits zero. The edge worker's JSON-LD facts must match visible page content.
5. For A2A discovery, read the current A2A specification's Agent Card and binding sections before writing code. Check whether the advertised endpoint already exists; if not, get a decision to build a real, bounded service rather than publishing a card that points to GitBook's 404. Keep the card's `supportedInterfaces`, capabilities, media types, and skills aligned with implemented behavior. A minimal read-only JSON-RPC directory may support only `SendMessage` and return verified public links, with streaming and push notifications explicitly false; reject unsupported methods and task/context operations, bound request bodies while reading, and never present unverified legal claims as answers. Test the card's GET/HEAD MIME and structure, a real POST response, malformed/oversized requests, and origin bypass. Scan the apex domain and inspect `checks.discovery.a2aAgentCard.status`; a passing card check does not prove unsupported agent features.
6. For a production change, obtain explicit deployment approval, identify the bound route and Worker, and compare the deployed script with the intended source before uploading. When using the Cloudflare API rather than Wrangler, retrieve the existing Worker content first, guard every targeted replacement with an exact-one-match assertion, and preserve its other code and configuration; do not overwrite a whole production Worker with a guessed stub. Read back the deployed Worker, then request the exact live URL: check HTTP status, plain-text response bytes against the original file, apex redirects if applicable, homepage Link header on GET and HEAD, and any homepage meta tag's count and position before `</head>`. For a discovery scanner, run the specified scan against the apex URL, inspect the precise nested check (for example `checks.discoverability.linkHeaders.status` versus `checks.discovery.authMd.status`), and report a failed auth-registration check honestly when no registration service exists. Never infer deployment or scanner success from a local test or a successful upload alone.
7. Return issue list by path/URL and severity, distinguishing local file state, GitBook-published state, and Cloudflare edge state. Include exact command exits and a baseline comparison for existing issues.

## Pitfalls
GitBook generates sitemaps and llms files; repo-root copies do not publish. `SUMMARY.md` label sets live title; metadata description comes from page frontmatter. A fenced JSON example is not live JSON-LD. No push, DNS change, WAF rule, or worker deployment without explicit authorization.

## Verification
Re-run the specific failed check after a fix and confirm the exact route or file; `git diff --check` for edits. If live checks are blocked, report the blocker and what remains unobserved.
